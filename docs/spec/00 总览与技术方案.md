## 结论与可行性

**结论：可行，建议立项。** mkagent 本身已经是“无界面后端 + 多客户端”架构：Electron、WebUI、CLI 三个客户端共用同一套带认证的 WebSocket RPC 协议，且已有独立的 headless server（`packages/server`）。GPUI 客户端只需成为“第四个客户端”，后端可以零修改或极少修改地复用。

真正的工作量在三处：

1. **UI 全量重写**：现有 React UI 约 8.6 万行（`apps/electron/src/renderer` 约 5.9 万行 + `packages/ui` 约 2.7 万行），需用 Rust + GPUI Kit 重写。MVP 只做核心工作台，约占其中 30%。
2. **Electron 专属能力替换**：Browser pane（第一版不做；原基于 Electron `BrowserView` + CDP）、窗口管理、自动更新、ChatGPT OAuth 回调、原生对话框、通知、菜单。
3. **Sidecar 打包**：把 headless server（含自带 Bun 运行时）与 Pi 子进程随 GPUI 应用一起分发并管理生命周期。

### 收益与代价

| 维度 | 收益 | 代价 / 说明 |
| --- | --- | --- |
| 界面性能 | GPU 渲染，长会话、流式输出、大 diff 下更流畅；GPUI Kit 自带虚拟化消息列表 `MessageScroller` | 需要自行做流式增量 Markdown 与帧合并 |
| 内存 | 去掉 Chromium 渲染进程，UI 侧内存显著下降 | Bun sidecar 与 Pi 子进程仍在，整体降幅取决于后端占用 |
| 安装包体积 | 去掉 Electron/Chromium | 后端自带的 Bun 运行时与工具资源较大，总体积降幅有限，不宜作为主要卖点 |
| 原生体验 | 原生窗口、菜单、快捷键、无障碍（AccessKit） | Linux Wayland 下 WebView 不可用 |
| 后端复用 | Agent 循环、会话 JSONL、权限引擎、Skills、模型连接全部复用 | 需跟随上游协议演进，做协议契约测试 |
| 开发效率 | Rust 类型安全，GPUI Kit 提供 75+ 组件 | 团队需具备 Rust + GPUI 能力，UI 迭代速度低于 React |

### 关键风险（详见文末）

- **Browser 工具无法用 WebView 平替**：WKWebView / WebKitGTK 没有 CDP，现有浏览器工具依赖 `Accessibility.getFullAXTree`、`Input.dispatchMouseEvent` 等 CDP 命令。因此第一版不做交互式浏览器，只保留 web\_search / web\_fetch；后续版本再按“独立 Chromium + CDP 浏览器宿主”方案补上。
- **GPUI 仍在快速演进**：GPUI Kit 当前为 v0.8.1，依赖 `gpui-pre =0.3.10`，存在破坏性变更，需锁版本并预留升级窗口。
- **上游协议漂移**：mkagent 仍在活跃开发（当前 v0.2.6），RPC 频道和事件可能变化。

## 两个项目的事实基础

以下内容基于 2026-10-28 对两个仓库 `main` 分支源码的阅读（mkagent v0.2.6，GPUI Kit v0.8.1）。

### mkagent：哪些能保留、哪些要替换

| 包 | 规模（非测试 TS 行数） | 职责 | 新方案中的处理 |
| --- | --- | --- | --- |

| `packages/shared` | \~4.3 万 | 协议 DTO、配置、凭据（AES-256-GCM 加密文件）、Skills、权限引擎、工作区存储 | **保留**；其协议类型是 Rust 端代码生成的来源 |
| `packages/pi-agent-server` | \~4.5 千 | Pi SDK 子进程，stdio JSONL 通信 | **保留** |
| `packages/session-tools-core` | \~3 千 | plan / skill / browser / mermaid 等会话工具 | **保留** |
| `packages/ui` | \~2.7 万 | React 组件与 Markdown/文档渲染 | **重写**为 Rust crate |
| `apps/electron/src/renderer` | \~5.9 万 | 聊天、设置、文件、浏览器 UI | **重写**为 GPUI 视图 |
| `apps/electron/src/main` | \~9.6 千 | 窗口、Browser pane、自动更新、深链、通知、代理 | **按清单替换** |

**协议要点**（`packages/shared/src/protocol/types.ts`）：

- 帧是 JSON `MessageEnvelope`，`type` 取值 `handshake / handshake_ack / request / response / event / error / sequence_ack`，协议版本 `1.0`。
- 客户端握手时携带 `token`、`workspaceId`、`clientCapabilities`；服务端在 `handshake_ack` 中返回 `clientId`、`registeredChannels`、`serverVersion`、`maxMessageBytes`。
- 可靠投递：事件带每客户端单调 `seq`，客户端每 5 秒发 `sequence_ack`；断线重连带 `reconnectClientId` + `lastSeq`，服务端缓冲 500 条 / 30 秒，`stale=true` 时需全量刷新。
- 心跳 30 秒，默认请求超时 30 秒。
- 会话实时事件走 `session:event` 频道，是 `SessionEvent` 联合类型（`text_delta`、`tool_start`、`tool_result`、`permission_request`、`plan_submitted`、`complete`、`usage_update` 等约 40 种）。
- **客户端能力（client capabilities）**：服务端可以反向调用客户端，如 `client:openExternal`、`client:openFileDialog`、`client:confirmDialog`、`client:browser:invoke`。这是原生客户端接管系统能力与浏览器的关键扩展点。

## 目标架构

总体思路：**GPUI 进程只负责界面、状态缓存与系统能力；Agent 能力全部留在 mkagent 后端**。两者之间只有一条本地 WebSocket RPC 连接，与现有 Electron 渲染进程走的是同一套协议。

高亮部分为新开发，灰底部分直接复用上游；虚线为第一版不包含、后续版本再加入的浏览器宿主。

### 一次对话回合的数据流

1. 用户在 `Composer` 输入并发送 → `SessionStore` 插入乐观消息 → `agentkit-client` 发送 `sessions:sendMessage`。
2. server-core 写入 `session.jsonl`，通过 stdio JSONL 让 Pi 子进程开始新回合。
3. Pi 流式返回 → server-core 推送 `session:event`（`text_delta`、`tool_start`、`tool_result`…）→ 客户端按 `seq` 排序后在 GPUI 前台归约 → 视图按帧刷新。
4. 工具需要授权时，服务端推送 `permission_request`，会话进入 `waiting_for_permission`；用户在 `PermissionPrompt` 点击后客户端调用 `sessions:respondToPermission`，同一回合继续。
5. 需要系统能力（打开链接、文件选择、确认框）时，服务端对该客户端发起 `client:*` 请求，由 `agentkit-capabilities` 处理并回复。
6. 回合结束推送 `complete`（含 Token 用量），会话回到 `idle`。

### 进程与线程

| 单元 | 语言 / 运行时 | 职责 |
| --- | --- | --- |
| GPUI 主线程 | Rust | 渲染、输入、Entity 状态 |
| RPC 线程 | Rust · smol | WebSocket 收发、重连、能力请求分派 |
| `mkagent-server` | 自带 Bun 运行 server.js | 会话、权限、配置、凭据、工具编排 |
| `pi-agent-server` | Bun 子进程 | Agent 循环、模型调用、工具执行 |

## 框架 crate 设计与扩展点

框架暂名 **AgentKit**（可替换）。交付物是一个 Cargo workspace：一组可复用 crate + 一个参考应用。下游团队 fork 参考应用或只依赖 crate，即可做出自己品牌的 Agent 桌面产品。

### 仓库结构

```
agentkit/
  Cargo.toml                 # workspace，锁定 gpui-kit = "=0.8.1"
  crates/
    agentkit-protocol/       # 协议类型（由 TS 生成）+ 频道常量
    agentkit-client/         # WS RPC 客户端：握手、请求、事件、seq ack、重连、能力处理
    agentkit-sidecar/        # 启动 / 监控 / 停止 mkagent-server
    agentkit-store/          # GPUI Entity 状态层：App / Workspace / SessionList / Session
    agentkit-ui/             # 可复用 Agent 组件：ChatView、Composer、ToolCard、PermissionPrompt…
    agentkit-capabilities/   # 原生能力：对话框、打开链接/文件、通知、OAuth 回调
    agentkit-browser/        # 浏览器宿主桥接（第一版不含，仅预留）
    agentkit-app/            # 应用骨架：AgentApp builder、Dock 布局、菜单、设置页
  apps/
    workbench/               # 参考应用（可直接发布的产品）
  backend/
    mkagent/                 # git submodule，锁定上游 tag
    patches/                 # 对上游的最小补丁（如有）
  tools/
    codegen/                 # TS 协议类型 → JSON Schema → Rust
  xtask/                     # 构建 sidecar、打包、签名
```

### 依赖方向

`protocol` ← `client` ← `store` ← `ui` ← `app` ← `apps/workbench`。`sidecar`、`capabilities`、`browser` 只被 `app` 依赖。`protocol` 与 `client` 不依赖 GPUI，可单独用于 CLI、测试或其他 Rust 宿主。

## RPC 客户端与协议实现规范

`agentkit-client` 必须与 mkagent 的 TS 客户端（`packages/server-core/src/transport/client.ts`）行为一致；以它和 `apps/electron/src/__tests__/transport.test.ts` 为对照实现。

### 协议类型代码生成（`agentkit-protocol`）

1. 用 `ts-json-schema-generator` 从 `@mkagent/shared/protocol` 导出 `MessageEnvelope`、`SessionEvent`、`Message`、`PermissionRequest`、`Session`、`FileAttachment` 等类型的 JSON Schema。
2. 用 `typify` 生成 Rust 类型；`SessionEvent` 生成为 `#[serde(tag = "type", rename_all = "snake_case")]` 枚举，并保留 `Unknown(serde_json::Value)` 兜底，避免上游新增事件时反序列化失败。
3. 频道常量从 `channels.ts` 的 `RPC_CHANNELS` 生成为 `pub const` 模块。
4. CI 中执行代码生成并比对 diff，上游升级时一次性暴露协议变化。

### 传输层要求

| 项 | 规范 |
| --- | --- |
| 运行时 | 独立线程上的 smol 执行器 + `async-tungstenite`（与 GPUI 生态一致，不引入 tokio）；与 GPUI 前台通过 `async-channel` 通信，不在 GPUI 线程阻塞 |
| 连接 | `ws://127.0.0.1:<port>`；远程模式支持 `wss://` 与自定义 CA（对应 `MKAGENT_TLS_CA`） |
| 握手 | 连接后 5 秒内发送 `{type:"handshake", protocolVersion:"1.0", token, workspaceId, clientCapabilities}`；保存 `clientId`、`registeredChannels`、`serverVersion`、`maxMessageBytes` |
| 请求 | `id` 用 UUIDv4；`invoke(channel, args) -> Result<Value, RpcError>`；默认超时 30 秒，`sessions:sendMessage` 等长调用单独设置（CLI 默认 300 秒） |
| 频道可用性 | 调用前检查 `registeredChannels`，不存在时返回 `CHANNEL_NOT_FOUND` 并在 UI 隐藏对应功能（headless 模式下 `window:*`、`update:*` 等可能不存在） |
| 事件 | `on(channel) -> Subscription`；按 `seq` 记录 lastSeenSeq（跳号只告警不重排，与上游一致），每 5 秒发送 `sequence_ack{lastSeq}` |
| 重连 | 指数退避（1s × 2ⁿ，上限 30s，连接稳定 10 秒后计数归零）；握手带 `reconnectClientId` + `lastSeq`；收到 `reconnected:true` 继续，收到 `stale:true` 触发全量刷新（重新拉取会话列表与当前会话消息） |
| 二进制 | 识别 `{"__craftRpcType":"u8","base64":…}` 包装，解码为 `Vec<u8>`；发送附件时同样编码 |
| 错误 | 解析 `WireError{code,message,data}`；`code` 保留为枚举 `ErrorCode`，未知值落入 `Other(String)` |
| 消息大小 | 发送前检查 `maxMessageBytes`，超限的附件先走 `file:storeAttachment` |
| 客户端能力 | 收到服务端发来的 `request`，按 `channel` 分派到已注册的能力处理器，回送 `response` 或 `error` |

## 状态管理与 UI 模块规范

### 状态层（`agentkit-store`）

全部状态用 GPUI `Entity<T>` 持有，视图通过 `cx.observe` / `cx.subscribe` 订阅。服务端是唯一事实来源，客户端只做缓存与乐观更新。

| Entity | 内容 | 更新来源 |
| --- | --- | --- |
| `AppState` | 连接状态、服务版本、已注册频道、当前工作区、主题 | 握手、重连 |
| `WorkspaceStore` | 工作区列表、默认权限模式、Skills、模型连接 | `workspaces:get`、`skills:changed`、`LLM_Connection:changed` |
| `SessionListStore` | 会话摘要（标题、状态、未读、置顶、归档）、Views 过滤 | `sessions:get`、`sessions:unreadSummaryChanged`、`session:event` 中的元数据事件 |
| `SessionStore`（每个打开的会话一个） | 消息列表、进行中的回合、工具调用树、待审批请求、计划、Token 用量、技术状态 | `sessions:getMessages` + `session:event` 归约 |

`SessionStore` 是一个纯函数归约器：`fn apply(&mut self, ev: &SessionEvent)`。要求：

- **可回放测试**：用录制的事件 JSONL 驱动，断言最终状态快照（见测试策略）。
- **工具调用树**：按 `toolUseId` 建索引，`parentToolUseId` 建父子关系，支持子 Agent / 后台任务（`task_backgrounded`、`task_progress`、`task_completed`）。
- **流式合并**：`text_delta` 先写入缓冲，每帧（约 16 ms）最多通知一次视图；`text_complete` 时以完整文本覆盖，`text_discard` 时丢弃该 `turnId` 的缓冲。
- **乐观消息**：发送时插入带 `optimisticMessageId` 的用户消息，收到 `user_message` 后替换。
- **状态机**：`idle → processing → waiting_for_permission → processing → idle`，以及 `failed`、`interrupted`；UI 按钮可用性只依赖这个状态。

### 流式 Markdown 性能

- 已完成的 Markdown 块解析后缓存为不可变元素，只对**最后一个未闭合块**重新解析（参考 GPUI Kit `examples/stream-markdown`）。
- 代码块高亮放后台线程，完成后再替换；流式期间先用等宽纯文本。
- 消息列表用 `MessageScroller`，只渲染可见区；单会话 5,000 条消息、10 万行工具输出时滚动保持 60 fps。

### UI 模块（`agentkit-ui`）

| 模块 | 主要组件 | 对应 mkagent 功能 |

### 交互与工程约定

- 所有可点击元素必须有无障碍角色与名称（GPUI Kit 内置 AccessKit）。
- 快捷键统一用 GPUI `actions!` 宏声明，集中在 `agentkit-app::keymap`，支持用户覆盖。
- i18n：沿用 mkagent 的英文 / 简体中文文案键，从 `packages/shared` 的 i18n 资源转换为 rust-i18n 格式（见 03 页），Rust 端用同一套键。
- 视觉风格遵循 GPUI Kit 的 Design Guides，主题只用语义 Token，不写死颜色。

### 浏览器工具：第一版不做

第一版**不提供交互式浏览器工具**，只保留 `web_search` 与 `web_fetch`。这两个工具完全在后端执行（未配置搜索 key 时回退到 DuckDuckGo），GPUI 端不需要任何浏览器实现，也不需要 Chrome。

第一版的具体做法：

- GPUI 客户端握手时**不声明** `client:browser:invoke` 能力。
- 工作区设置中的 `browserToolEnabled` 默认关闭，避免把 `mcp__session__browser` 暴露给模型；若仍被调用，服务端返回 `BROWSER_NO_CAPABLE_CLIENT`，`ToolCard` 显示“当前版本不支持浏览器操作”。
- 设置页不展示浏览器相关开关。
- **需验证**（阶段 0）：关闭开关后，该工具确实不出现在模型的工具列表中（上游 `session-tools-core` 有工具过滤逻辑 `tool-defs-filtering`）。

后续版本方向（不在本期范围）：系统 WebView（WKWebView / WebKitGTK）没有 CDP，无法支撑 Agent 操作网页。届时采用“优先用系统 Chrome、缺失时按需下载 Chrome for Testing + 并入 `mkagent-server` 的 CDP 浏览器宿主”方案，可复用 Electron 版 `browser-cdp.ts` 约 1,400 行逻辑，不增加安装包体积。

## Sidecar 打包、分发与升级

### 构建产物

| 产物 | 来源命令 | 放置位置 |
| --- | --- | --- |
| 后端目录：`server.js` + 自带 Bun 运行时 + `resources/`（含 Pi 子进程、uv、文档工具脚本）+ ripgrep | `bun run scripts/build-server.ts --no-webui`（补丁 P-03） | 应用包 `Resources/backend/` |
| GPUI 应用 | `cargo build --release` | 主可执行文件 |

完整目录布局与环境变量见 07 页。

`xtask package` 负责：拉取锁定 tag 的 `backend/mkagent` → 构建以上产物 → 组装应用包 → 签名。macOS 需对 sidecar 二进制单独签名并启用 hardened runtime；Windows 需对所有 `.exe` 做 Authenticode 签名。

**已核实**：上游 headless 构建本身就把 Bun 运行时复制到 `vendor/bun/`，Pi 子进程由它运行，用户无需安装 Bun 或 Node。剩余待验证项是 Bun 在 macOS hardened runtime 下所需的 JIT entitlements（任务 T-0-09）。

### 生命周期（`agentkit-sidecar`）

1. 生成 32 字节随机 token；端口传 `0`，由系统分配。
2. 以 `vendor/bun/bun server.js` 启动，环境变量含 `CONFIG_DIR`、`MKAGENT_SERVER_TOKEN`、`MKAGENT_RPC_HOST=127.0.0.1`、`MKAGENT_RPC_PORT=0` 等（完整列表见 07 页），并合并用户登录 shell 的 PATH。
3. 读取 stdout，等待 `MKAGENT_SERVER_URL=` 一行作为就绪信号并解析实际端口（超时 15 秒）；`MKAGENT_SERVER_TOKEN=` 行不得写入日志。
4. 就绪后建立 RPC 连接；之后用 `server:getHealth` 做健康检查。
5. 子进程异常退出：60 秒内至多自动重启 3 次，会话由后端标为 `interrupted`；超过次数显示阻断页与“查看日志”。
6. 应用退出：先 `sessions:cancel` 进行中的会话，再对进程组发 SIGTERM，5 秒后 SIGKILL；Windows 用 Job Object 保证主程序崩溃时子进程一并退出。
7. 端口与 token 只保存在内存，不落盘。

**数据目录**：使用独立目录 `~/.agentkit`（通过 `CONFIG_DIR` 传入），不与 Electron 版共用 `~/.mkagent`。原因：后端对配置目录加单实例锁，共用会导致两个应用无法同时运行。迁移方式见 07 页。

### 升级

- 推荐 **Velopack** 或 `cargo-packager` 的 updater：一次更新同时替换 GPUI 主程序与 sidecar，保证前后端版本一致。
- 握手时比对 `serverVersion` 与客户端编译时记录的兼容范围；不兼容时阻止连接并提示重装，而不是带病运行。
- 发布渠道沿用 GitHub Releases，清单公开，客户端不内嵌任何 token（与上游 `electron-updater` 策略一致）。
