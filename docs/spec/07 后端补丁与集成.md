# 07 后端补丁与集成

本页说明如何锁定、构建、修补并启动 mkagent 后端。

## 上游锁定与同步策略

- 上游以 git submodule 放在 `backend/mkagent`，锁定 tag **v0.2.6**（commit `6e8ebc456b6b82441be09118ca11afca79b84836`）。本文档全部频道、字段与文件路径均以该提交为准。
- 补丁放在 `backend/patches/*.patch`，由 `cargo xtask backend build` 在构建前依次 `git apply`；任何补丁应用失败即构建失败。子模块目录内不得提交本地修改。
- 每个补丁同时向上游提 PR；上游合并后的第一次升级中删除该补丁。
- **升级流程**（每月评估一次，或上游有安全修复时立即）：移动子模块到新 tag → `xtask backend build` → `xtask codegen` 并审阅生成代码 diff → 对照上游 `event-processor` 与 `turn-utils` 的变更同步 Rust 移植 → 契约与夹具测试全绿 → 单独 PR（标题 `chore(backend): bump mkagent to vX.Y.Z`）。
- 上游协议出现破坏性变化（`PROTOCOL_VERSION` 变更、已用频道改名或参数变化）时，先写一页设计说明（ADR）再升级。

## 后端补丁清单与具体改法

共 3 个补丁，均不改变上游 Electron 版行为。补丁 P-01、P-02 放在新文件中，只由 headless 入口注册，以避免与 Electron 主进程的同名处理器（`apps/electron/src/main/handlers/settings.ts` 的 `registerSettingsGuiHandlers`）重复注册。

| 编号 | 问题 | 改法 | 涉及文件 |
| --- | --- | --- | --- |
| P-01 | `settings:setNetworkProxy` 只在 Electron 主进程注册，headless 后端无法保存代理；且 headless 后端启动时不会把已保存的代理应用到自身进程 | ① 新增 `registerHeadlessDesktopHandlers(server)`：注册 `settings:setNetworkProxy(settings)`，调用 `setNetworkProxySettings(settings)` 保存并返回 `{ restartRequired: true }`。② 新增 `applySavedProxyToProcess()`：读取已保存设置，用与 Electron 版 `network-proxy.ts` 相同的 `ProtocolProxyDispatcher`（undici，尊重 NO\_PROXY）设置全局 dispatcher，去掉其中 Electron `session.setProxy` 部分。③ 在 headless 入口启动时调用 ②，并在 `registerAllRpcHandlers` 回调中调用 ① | 新增 `packages/server-core/src/handlers/rpc/headless-desktop.ts`、`packages/server-core/src/services/headless-proxy.ts`；修改 `packages/server/src/index.ts` |
| P-02 | `power:setKeepAwake` 只在 Electron 注册 | 在 ① 的同一函数中注册：只调用 `setKeepAwakeWhileRunning(enabled)` 保存设置；实际防休眠由客户端执行 | 同 P-01 |
| P-03 | `scripts/build-server.ts` 始终构建并拷贝 WebUI，并断言 `webui/index.html` 存在 | 增加 `--no-webui` 参数：跳过 `webui:build`、拷贝与对应断言；其余产物不变 | `scripts/build-server.ts` |

协议类型导出不需要改上游：`tools/codegen` 直接以子模块中的 TS 源码为输入运行 `ts-json-schema-generator`（入口 `packages/shared/src/protocol/index.ts` 与 `packages/core/src/types/index.ts`），再用 `typify` 生成 Rust。`typify` 处理不了的类型（如交叉类型、模板字面量）在 `tools/codegen/overrides/` 手写并在生成时覆盖。

补丁验收：上游 `bun run validate:ci` 在打补丁后仍全绿；契约测试覆盖 P-01（设置 → 重启 → 读回一致）与 P-02。

## sidecar 构建产物布局与启动参数

上游 `scripts/build-server.ts` 产出的不是单文件二进制，而是“JS 包 + 自带 Bun 运行时 + 资源目录”。Pi 子进程由自带 Bun 运行 `resources/pi-agent-server/index.js`，因此**不需要用户安装 Bun 或 Node**。`cargo xtask backend build` 调用 `bun run scripts/build-server.ts --no-webui --output=<目标目录>`，得到：

```
backend/
  server.js                                   # 后端主程序（bun build 产物）
  vendor/bun/bun[.exe]                        # 自带 Bun 运行时
  resources/
    pi-agent-server/index.js                  # Pi 子进程
    bin/ 与 bin/<平台>-<架构>/uv[.exe]         # uv 等工具
    scripts/                                  # 文档工具脚本
  node_modules/@vscode/ripgrep/bin/rg[.exe]  # ripgrep
  node_modules/xlsx/
  mkagent-server[.cmd]                        # 上游启动脚本，我们不使用
```

上游构建必须在目标平台上执行（脚本会拒绝交叉构建），故 CI 的 `package` 作业按平台分别构建。

**sidecar 启动命令**：`<backend>/vendor/bun/bun <backend>/server.js`，工作目录 `<backend>`。环境变量（等同上游启动脚本，另加 ★ 项）：

| 变量 | 值 |
| --- | --- |
| `CONFIG_DIR` ★ | `~/.agentkit`（取自 brand） |
| `MKAGENT_SERVER_TOKEN` ★ | 每次启动随机 32 字节 hex |
| `MKAGENT_RPC_HOST` ★ / `MKAGENT_RPC_PORT` ★ | `127.0.0.1` / `0`（后端允许 0 并在就绪行输出实际端口） |
| `MKAGENT_VERSION` ★ | 应用版本 |
| `MKAGENT_BUNDLED_ASSETS_ROOT`、`MKAGENT_APP_ROOT` | `<backend>` |
| `MKAGENT_RESOURCES_PATH` | `<backend>/resources` |
| `MKAGENT_IS_PACKAGED` | `true` |
| `MKAGENT_UV` | `<backend>/resources/bin/<平台>-<架构>/uv[.exe]` |
| `MKAGENT_SCRIPTS` | `<backend>/resources/scripts` |
| `PATH` | `<backend>/resources/bin` + `<backend>/resources/bin/<平台>-<架构>` + `<backend>/vendor/bun` + **用户登录 shell 的 PATH**（见下） |
| 不设置 | `MKAGENT_WEBUI_DIR`、`MKAGENT_RPC_TLS_*`、`MKAGENT_HEALTH_PORT` |

**用户 shell 环境**：macOS 从 Finder / Dock 启动的应用只有最小 PATH，Agent 的 bash 工具会找不到 Homebrew、nvm 等工具。sidecar 启动前按上游 `apps/electron/src/main/shell-env.ts` 的做法，执行一次用户登录 shell（`$SHELL -ilc env`，超时 5 秒）获取完整环境变量并合并传给 sidecar；结果在本次应用运行期间缓存。Windows / Linux 直接继承当前进程环境。

**就绪信号**：后端在 stdout 依次输出 `MKAGENT_SERVER_URL=ws://127.0.0.1:<port>` 与 `MKAGENT_SERVER_TOKEN=<token>`；前者为就绪信号，后者必须从日志中滤掉。

## 与 MkAgent Electron 版的共存与数据迁移

- **为什么不共用数据目录**：后端启动时在配置目录写 `.server.lock`，发现另一个存活的后端就拒绝启动（“Another server instance is already running”）。两个应用共用 `~/.mkagent` 就不能同时运行。因此本应用使用独立目录 `~/.agentkit`，两者可以同时安装、同时运行。
- **端口**：本应用使用随机端口，不占用上游默认的 9100。ChatGPT OAuth 回调端口 1455 是固定的，两个应用同时发起登录会冲突，提示用户先完成另一个登录即可。
- **迁移路径（v1）**：用户在 Electron 版中导出会话，再在本应用“文件 → 导入会话”（F-14）。模型连接与密钥不迁移，需重新添加。
- **批量迁移（v1 之后可选）**：“从 MkAgent 导入”向导，在 MkAgent 未运行时（无存活锁）把 `~/.mkagent/workspaces/` 下的工作区与会话复制到 `~/.agentkit/`，不复制凭据文件。未列入 01 页功能清单。
