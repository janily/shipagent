# T-1-02 本地完整 client 协议验证

日期：2026-11-01。基线 main 8023694（PR #7 已合并）。后端仍固定 v0.2.6 / 6e8ebc456b6b82441be09118ca11afca79b84836，未改子模块或补丁。PR #6 工程包保持原样，真实 Developer ID/公证继续按用户决定暂缓。

## 已实现

- 本地 WebSocket 连接/握手/退避/关闭/Fatal；状态订阅、握手元数据和频道能力查询；固定1/2/4/8/16/30秒退避，稳定10秒才重置。
- 重连带原 clientId/最大 seq，失败握手不丢游标；fresh/stale/服务端身份变化发出全量刷新通知；保留订阅，5秒 ack、ping/pong、跳号警告。
- 同步请求代际屏障：断线清掉旧队列和挂起请求，不重发写；端点替换中断旧连接/退避并清游标；工作区切换只在成功响应后更新绑定。
- 能力分派独立任务、超时、并发上限、未知/异常/过大结果回错；断线取消旧 future，禁止跨连接回包；默认不注册系统动作，始终不声明 browser。
- RpcValue 二进制调用/订阅，原始 JSON API 同样检查损坏包装；UTF8/base64 后的大小检查，接收帧上限16MiB。
- 显式只读 invoke_read 只对超时重试一次；普通调用不重试；protocol_code 提供稳定错误码。类型化会话事件流保留未知事件并返回解码错误。
- 原型 UI 断线禁用操作；无缺口续传可恢复，fresh/stale 必须手动重新加载。控制器检查代际，避免状态监测间隔内发送陈旧操作；保留草稿。

此处“完整”指 T-1-02 本地传输协议，不代表所有应用功能交付。完整 API 门面 T-1-03、原生能力实现 T-1-19、自动缓存重建/正式恢复 UX T-1-08/21、远程 TLS/自定义 CA T-4-03 均未提前宣称完成。二进制 API 使用 RpcValue；原始 Value 接口仍保留包装格式。typed session_events 返回 Result，避免吞掉坏载荷。

## 测试与缺陷证据

首批测试先复现“断线不重连”和“坏 base64 被普通 Value 接受”，再实现并通过。后续修正：

1. 断线清理执行两次，误取消刚入队的新一代请求：真实 TCP 回归复现，改为只失效一次。
2. 已超时/取消请求的零期限误关闭健康连接，使只读重试变成 Disconnected：实际请求超时、旧 id 延迟响应和新 id 重试测试复现；IO 期限排除失效项。
3. stale 恢复误启用发送：原生控件测试先失败，再验证禁发和草稿保留；控制器另有纯策略测试覆盖监测尚未触发的间隙。
4. GPUI 通配导入遮蔽内建 #[test]，导致宏递归：采用已有 perf 测试相同的全限定内建属性，没有提高递归上限。

本地最终命令及最终三平台结论以本分支提交检查和 PR 描述为准：`cargo test --locked`、全功能 clippy -D warnings、原生 UI/App 测试、fmt、codegen --check；真实 bundled backend + Pi + 本地 SSE 模型的 Read/流式/持久化/取消契约另显式通过。默认 suite 中真实后端用例仍 ignored，不把默认通过冒充已运行。

传输夹具使用真实 TCP/WebSocket和有期限的同步信号，不以 OS 缓冲区必然阻塞为假设。单测覆盖过期队列、断线写不重发、fresh/stale/续传、失败握手保留 cursor、最大 seq、端点/token/元数据替换、工作区成功绑定、close 中断退避、状态流关闭、慢能力与事件并发、能力异常/超时/体积、旧任务取消、base64膨胀、只读重试和未来事件。

三平台矩阵保持 Linux、macOS15 arm64、Windows2022 x64；窗口提交与单独后端契约不能拼成完整主应用物理桌面验收。阶段0依旧未通过，见 [风险报告](phase-zero-risk-report-2026-10-31.md)。
